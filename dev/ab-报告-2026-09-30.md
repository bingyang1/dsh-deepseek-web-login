# A/B 实测报告：上下文投喂 full vs chained

**日期**：2026-09-30 17:35　**脚本**：`.workbuddy/tmp/ab-context-feed.mjs`（可复用：`node ab-context-feed.mjs full|chained [步数]`）

## 为什么要做这个测试

用户观察到「思考过程中反复出现同一句话」（红框：`你确定安装好了？？那为啥没有设置页面呢`）。
上一个会话的取证结论是：那段会话 **102 段思考＝102 次模型调用**，那句原话在思考里出现 **48 次 / 27 段**；
机制是「每调一次工具＝一次全新模型请求，而模型看不到自己上一轮的思考 ⇒ 每段都从'用户要什么'重新起手」。
本测试验证的假设是：**换成链式投喂（模型能接着自己上轮的思路）会不会减少这种复述**。

## 做法

- **复用插件自己的 `createAdapter`**（真实协议序列化 + 真实网页端请求 + 真实工具调用协议），
  上面套一个最小 agent loop，复刻 DSH 的循环：一次模型调用 → 执行工具 → 把结果作为 `tool-result` 回喂 → 再调一次。
- 同一道任务、同一个账号（`acc_cedc94e2`，**非活动号**，避免和正在运行的 DSH 抢账号/会话）、
  同一个闸门配置（2~4 秒，沿用生产密度），`full` 与 `chained` 各跑 5 次模型调用。
- **关键手段：抓请求体**（`setFetchImpl` 包一层）—— 直接读每一轮真正发出的 `prompt` 长度与
  `parent_message_id`。只看 `usage` 里的 token 估算是**分不出**"链真的接上了"和"每轮悄悄退回全量"的。

## 结果

| 指标 | full | chained |
|---|---|---|
| 每轮 prompt 字符 | 3364 → 3547 → 3683 → 3835 → 3998（线性增长） | 3364 → **181 → 134 → 150 → 161** |
| 5 轮 prompt 合计 | **18,427 字符** | **3,990 字符（-78%）** |
| `parent_message_id` | 全部 `null`（根消息＝每轮全量） | `2 / 4 / 6 / 8`（**真的挂上链**，4/5 次） |
| 用户原话被复述 | 0 次 / 5 段 | 0 次 / 5 段 |
| 思考字数（5 段合计） | 435（另一次跑 179） | 115（另一次跑 134） |
| `usage` 估的输入 token | 4,963 | 5,459 |

原始数据：`ab-full-1790761067055.json`、`ab-chained-1790761035407.json`（同目录）。

## 结论

1. **chained 确实生效**：第 2 轮起每轮只发 134~181 字符，其余历史由服务端按父链维护。
   **上传量降到 full 的约五分之一（-78%）。**
2. **但它不省 token**：两边 `usage` 估的输入几乎一样（4,963 / 5,459）。那个数是按
   「模型要读的整段上下文」估的 —— 服务端仍要把整段历史拼起来给模型读。
   ⇒ **要省 token 只能压历史（`contextWindow` / 会话清理），换投喂模式没用。**
   chained 真正省的是**上传字节**（也就是"每轮重发一份完整提示词"这种机器行为的表面积）。
3. **对"复述"这件事，本测试没能复现**（两组都是 0 次）—— 合成任务比真实会话简单太多，
   真实那段是每段思考平均 7,400 字的硬任务。所以**不能说"切 chained 就消掉复述"**。
   但有一处**结构差别是确定的**：full 每轮都把用户那句原话重新发一遍（5 轮＝5 次再现），
   chained 只在链首发 1 次 ⇒ 想少看到复述，chained 只会更少、不会更多。
   主导因素仍是**任务难度/不确定性**，不是投喂模式。
4. **chained 的代价**（README 与代码里写明）：系统提示、工具协议、历史全在**链首那条消息**里 ——
   服务端一旦丢掉早期上下文，模型可能不按约定 JSON 发工具调用；插件遇任何不确定会**自动退回全量重发**。
   另外**改 head（协议指令 / 工具目录 / system）会让链断一次**。

## 建议

- 想减少"每轮重发一份完整提示词"的表面积、让请求更像真人连续对话 ⇒ **值得切 `chained`**
  （面板：设置 → DeepSeek 网页登录 → 上下文投喂）。
- 想省 token ⇒ 切投喂模式**没有**；去压「上下文范围」与「会话清理」。
- 想减少思考里的复述 ⇒ 没有开关能直接解决，那是 reasoning 模型在**无状态循环**里的固有起手式。
